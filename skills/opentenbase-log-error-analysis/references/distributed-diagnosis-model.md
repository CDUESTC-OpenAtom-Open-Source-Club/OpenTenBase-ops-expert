# OpenTenBase 分布式诊断模型与事务/健康判断

本文件是 OpenTenBase 故障诊断的长期认知底座，日志分析、启动/连接故障、集群健康判断、事务与 2PC 排查时优先参考。具体命令、系统表字段必须结合当前版本确认。

## 1. 事务、一致性与全局对象

- 只访问一个 DN 的事务通常比同时访问多个 DN 的事务简单、开销更低。
- 跨 DN 写入属于分布式事务，需要全局事务协调，并可能使用两阶段提交（2PC）保证原子性。
- 异常中断后，除了普通会话和锁，还应考虑是否存在 prepared/2PC 事务残留。
- 普通锁等待、分布式死锁和 prepared 事务残留是不同问题，应分别判断。
- 分布式事务可能在多个 CN 和 DN 之间形成跨节点等待环；单个节点的锁信息可能无法反映完整依赖链。
- 长事务会延长锁和快照生命周期，在分布式环境中影响范围可能更大。
- 序列等对象需要全局协调，不能按单个 DN 的局部对象理解。
- 应用在事务结果不确定时不能盲目重试写操作，必须考虑幂等性。

### 2PC / prepared 事务残留的影响

- 残留的 prepared 事务会长期持有锁、阻塞其他事务、延缓资源回收。
- 它们还会拖住相关表的清理（VACUUM），长期积累可能引发更严重的连锁问题。
- 排查时应在相关节点确认是否存在挂起的 prepared 事务，并结合业务判断是提交还是回滚——绝不盲目清理。

## 2. 高可用与健康判断

- CN、DN 和 GTM 都可能具有主备实例，不同角色故障造成的影响不同。
- 主备切换不仅是提升新主，还必须保证其他节点使用的角色和路由信息与实际拓扑一致。
- 进程存活只说明操作系统进程存在，不代表数据库一定可连接、复制正常、角色正确、路由有效或事务服务可用。
- 端口监听也不等于集群健康。
- 集群健康应综合判断：进程、数据库连接、节点角色、复制状态、路由一致性、事务能力和实际 SQL 可用性。

### 健康判断的递进层次（"进程在" ≠ "健康"）

1. 操作系统进程是否存在；
2. 端口是否监听；
3. 数据库是否可连接（`psql` 能否登录）；
4. 节点角色是否正确（主/备、CN/DN/GTM 角色符合拓扑）；
5. 复制状态是否正常（主备延迟在可接受范围）；
6. 路由是否一致（各 CN 看到的节点/分布元数据一致）；
7. 事务服务是否可用（能否正常开启/提交跨节点事务）；
8. 实际业务 SQL 是否可正常执行。

## 3. 基本诊断模型

分析 OpenTenBase 问题时，先确认：

1. 当前版本、实例类型、部署方式和实际拓扑；
2. 问题位于客户端、CN、DN、GTM、网络还是操作系统；
3. 涉及表的类型、分布键、分区键和 Group；
4. SQL 实际访问哪些节点；
5. 是否存在广播、数据重分布或 CN 集中汇总；
6. 是否涉及跨节点事务、锁、2PC、复制或主备切换；
7. 是否存在数据倾斜或不同 DN 统计信息不一致；
8. 最后检查索引、CPU、内存、磁盘和网络资源。

没有版本、拓扑、表定义、执行计划和实际错误信息时，不应对故障原因作确定性判断。

## 4. 日志定位的分布式视角

- CN 日志：SQL 解析/路由错误、连接 GTM 或 DN 失败、全局事务协调异常。
- DN 日志：本地执行错误、磁盘/内存问题、与 CN 的通信异常。
- GTM 日志：全局事务/序列服务异常、连接被拒。
- 定位时把日志时间、节点名、节点角色、端口、进程和连接结果对齐后再下结论，不要只看单节点日志就断因。
- 一个节点的报错常常是另一个节点问题的"外在表现"（例如 CN 报 "connect to DN failed" 的根因在 DN 侧或网络）。
