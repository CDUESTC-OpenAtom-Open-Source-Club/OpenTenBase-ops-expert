# OpenTenBase 分布式核心知识

本文件是 OpenTenBase 分布式架构、数据分布与 SQL 路由的长期知识底座。SQL 调优、分布键设计、跨节点 Join、执行计划分析时优先参考本文件。具体命令、路径、参数、系统表字段和版本特性必须结合当前环境确认。

## 1. 产品与部署形态

- OpenTenBase 是 PostgreSQL 生态中的开源分布式数据库，面向高并发、大数据量和 HTAP 场景。
- 它兼容 PostgreSQL 协议、客户端和大量 SQL 语法，但不能假设所有 PostgreSQL 功能和行为都完全一致。
- OpenTenBase 实例可能采用分布式或集中式形态。分析问题前应确认版本、实例类型和实际拓扑。
- 数据分布、节点管理、SQL 方言、兼容范围和管理工具可能随版本变化。

## 2. 分布式核心架构

分布式 OpenTenBase 集群主要由 CN、DN 和 GTM 构成。

- **Coordinator（CN）**：应用访问入口，保存全局元数据，负责 SQL 解析、规划、路由、任务下发和结果汇总，通常不保存分片业务数据。
- **Datanode（DN）**：保存实际业务数据分片，执行 CN 下发的查询和写入任务。
- **Global Transaction Manager（GTM）**：管理全局事务信息以及序列等全局对象，不保存业务数据。
- 普通应用、DDL 和 DML 通常通过 CN 执行。CN 将任务发送到一个或多个 DN，再汇总结果。
- 直接连接 DN 通常用于诊断、维护或明确要求的底层操作，不应将 DN 作为普通业务入口。
- CN 与 DN 需要保持一致的数据库对象定义和必要的路由信息。

逻辑节点与物理服务器不是同一概念。一台服务器可以运行多个节点，一个节点角色也可能具有主备实例。

### 开发者速记：用大白话理解分布式数据库

这部分用普通开发者的视角，把分布式数据库的核心概念讲清楚。

**DN 是"分片"而不是"全量数据源"**

每个 DN 只存数据的一部分，不是全部。想象 `users` 表有 100 万行数据：

```sql
CREATE TABLE users (id int PRIMARY KEY, name text) DISTRIBUTE BY SHARD(id);
```

CN 根据分片键（上例中的 `id`）的哈希值，决定每一行数据存到哪个 DN：

```
DN1: id=1,3,5,7,...（约 50 万行）
DN2: id=2,4,6,8,...（约 50 万行）
```

建表时可以指定分片键，不能靠未经验证的默认分布规则。只在非分片键上创建唯一约束可能无法由各 DN 独立保证全局唯一。

**主备 (Replication)：一份数据存两份**

如果有主备（高可用模式），每个分片的数据会在另一台机器上多存一份相同的副本：

```
DN1 主 (机器1)    DN1 备 (机器2)
id=1 张三         id=1 张三      ← 同一份数据
id=3 王五         id=3 王五
```

主备存的是同一份数据，目的是机器挂了能顶上，数据不丢。

**容量直观计算**

- **无主备（测试环境）**：2 台机器，每台 100GB。DN1 存 50GB，DN2 存 50GB，总可用容量 = 100GB，两台都用上了。
- **有主备（高可用）**：同上配置，但 DN1 备也占 50GB，DN2 备也占 50GB，总可用容量 = 100GB，但一半空间给了备份。

**角色类比表**

| 角色 | 类比 | 说明 |
|------|------|------|
| **CN** | 前台小姐姐 | 你问她问题，她去找对应的人拿答案，自己不存业务数据 |
| **DN** | 后面干活的人 | 每人管一部分数据，存实际业务数据分片 |
| **GTM** | 记账先生 | 确保全局事务顺序不乱，不存业务数据 |
| **分片 (Sharding)** | 拆 Excel | 把大文件拆成小文件，每人拿一部分 |
| **主备 (Replication)** | 复印 Excel | 把每份小文件复印一份放别处，防止丢失 |

**查询路由实例**

点查（带分片键）—— 只访问一个 DN：
```
你：SELECT * FROM users WHERE id = 2
CN：id=2 哈希→在 DN2 上 → 只问 DN2，不问 DN1 → 返回结果
```

全表扫描（不带分片键）—— 广播到所有 DN：
```
你：SELECT * FROM users
CN：同时问 DN1 和 DN2 "把你们的数据都给我"
DN1、DN2 并行返回各自数据 → CN 合并后给你
```

分析执行计划时，需要关注 SQL 被发送到哪些节点、是否出现广播或远程执行、是否发生数据重分布，以及 Join、排序、聚合在哪一层执行。

## 3. 拓扑与集群元数据

- 节点名称、角色、地址、端口、主备关系和数据 Group 共同构成集群拓扑。
- **Group** 是组织 DN 或分片存储范围的逻辑单位，用于限定表的数据存放位置。
- **Shard** 是逻辑数据路由单位。分布键经过计算后定位到 shard，再根据映射访问实际 DN；具体数量和映射机制属于版本及实现细节。
- CN 根据节点、Group、shard 和表分布元数据确定 SQL 应访问哪些 DN。
- 节点进程已经启动，不代表节点角色、路由和集群元数据一定正确。
- 拓扑发生变化后，相关节点对主备角色和路由位置的认知必须与实际情况一致。
- 拓扑管理语句修改的是集群级元数据，不能按普通业务 DDL 理解。

## 4. 表类型、分片与分区

常见的数据组织方式包括：

- **分片表**：按分布键将记录分散到不同 shard 和 DN，适合大数据量业务表。
- **复制表**：在相关 DN 上保存完整副本，适合数据量小、更新较少、经常参与关联的字典表或维度表。复制表不适合大型或高频更新表。
- **单分片表**：将表放在只包含单一分片的数据 Group 中，适合数据量较小且不需要横向分布的场景。
- **分区分片表**：在逻辑表内部划分分区，同时按分布规则将数据放到不同节点。

分区和分片解决的问题不同：

- 分区决定记录属于表内哪个子分区。
- 分片决定记录位于哪个 shard 和 DN。
- 二者可以组合使用，分区裁剪和分片路由需要分别分析。

## 5. 分布键

分布键决定数据路由、事务范围、Join 方式和数据均衡，是分布式表设计的核心。

选择分布键时应考虑：

- 是否经常出现在查询、更新和删除条件中；
- 是否是大表之间的常用 Join 字段；
- 是否能减少一次操作访问的 DN 数量；
- 数据值是否足够分散，避免热点和数据倾斜；
- 字段是否长期稳定；
- 是否符合业务事务边界。

主键不一定是最佳分布键。只追求分布均匀而忽略访问路径，也可能造成广播查询、跨节点事务和数据重分布。

分布键、分区键及相关字段的修改通常受到限制，具体行为必须按当前版本确认。创建业务表时应尽量显式指定分布方式，不依赖未经验证的默认规则。

## 6. OpenTenBase SQL 方言

应识别以下分布式语法：

```sql
DISTRIBUTE BY SHARD(column)
```

表示按指定分布键创建分片表。

```sql
DISTRIBUTE BY REPLICATION
```

表示创建复制表。

```sql
TO GROUP group_name
```

表示指定表所属的数据 Group。

还应识别以下类型的集群级语句：

```sql
CREATE NODE ...
ALTER NODE ...
CREATE NODE GROUP ...
CREATE SHARDING GROUP ...
CLEAN SHARDING ...
```

这些语句涉及节点、Group、分片或路由元数据，不是普通业务 DDL，可能改变集群拓扑或数据布局。

部分版本还提供扩展分区、周期分区、增加分区和按分区值操作等语法。精确写法和限制应查阅当前版本文档。

常规数据库、Schema、用户、角色、权限、索引和 DML 大体遵循 PostgreSQL 使用习惯；主要差异集中在数据分布、节点、Group、路由、全局对象和分布式事务。

## 7. SQL 路由与执行

- 带有可路由的分布键等值条件时，SQL 通常只需访问一个或少量 DN。
- 无法根据条件定位数据时，SQL 可能被发送到全部相关 DN，再由 CN 汇总。
- 两张大表采用兼容的分布方式，并按相同分布键关联时，更容易在 DN 本地完成 Join。
- 分布方式不兼容时，可能发生数据重分布，增加网络、内存和计算开销。
- 大量中间结果返回 CN 处理时，CN 和网络可能成为瓶颈。
- 增加 DN 数量不会使所有 SQL 自动变快；广播、跨节点 Join 和集中汇总可能产生更多开销。

分析执行计划时，除索引和扫描方式外，还应关注：

- SQL 被发送到哪些节点；
- 是否出现广播或远程执行；
- 是否发生数据重分布；
- Join、排序、聚合在哪一层执行；
- 是否发生分区裁剪和分片路由；
- 估算行数与实际行数是否偏差明显；
- 不同 DN 是否存在执行时间和计划差异。

## 8. 索引、约束与统计信息

- 索引解决单节点数据访问效率，不能代替合理的数据分布设计。
- 分片表的主键和唯一约束必须与分布方式一起设计。
- 仅在非分布键字段上定义唯一约束，可能无法由各 DN 独立保证全局唯一；具体限制应按当前版本确认。
- 大表 Join、唯一性要求、分布键和业务主键应在建模阶段统一考虑。
- PostgreSQL 的统计信息、索引、VACUUM 和 ANALYZE 原理仍然重要，但需要从各 DN 的角度理解。

数据倾斜可能表现为：

- 各 DN 行数或数据量明显不一致；
- 某些 DN 负载和响应时间更高；
- 不同 DN 选择不同执行计划；
- CN 汇总等待少数慢节点。

分析倾斜时，应比较各 DN 的行数、表大小、统计信息和本地执行计划，不能只观察 CN 的汇总结果。

## 9. PostgreSQL 基础与分布式差异

以下 PostgreSQL 基础原理仍然适用：

- MVCC、事务隔离和锁；
- 索引与统计信息；
- VACUUM 和 ANALYZE；
- `psql` 和常见 PostgreSQL 驱动。

但在 OpenTenBase 中还必须同时考虑：

- 数据分布和 SQL 路由；
- 跨节点网络通信；
- 分布式事务；
- CN 汇总压力；
- 各 DN 的数据量和计划差异；
- 分布方式对约束和 Join 的影响；
- 集群级对象和拓扑元数据。

## 10. 应用开发认知

- 应用通常通过 CN 访问数据库，不应将 DN 作为普通业务入口。
- 生产接入应考虑多个 CN 的可用性，避免长期绑定单一接入点。
- 表设计不能只确定主键和索引，还要同时确定表类型、分布键、分区键、唯一性要求和主要访问路径。
- 唯一约束、跨表 Join、批量写入和事务边界可能受到数据分布方式影响。
- 批量操作应尽量按分布键组织数据，减少随机跨 DN 访问。
- PostgreSQL 驱动通常可以使用，但协议兼容性、特殊数据类型和版本差异仍需验证。
- 连接池、故障重试和事务重试必须考虑节点切换、事务状态和操作幂等性。

## 11. 必须避免的误区

- 所有 OpenTenBase 环境都具有相同的 CN、DN 和 GTM 拓扑。
- CN 保存主要业务数据。
- GTM 保存业务数据。
- 可以将 DN 作为普通应用入口。
- DN 越多，任何 SQL 都越快。
- 创建索引后就不需要考虑分布键。
- 主键一定是最佳分布键。
- 分区和分片是同一概念。
- 表权限自动包含 Schema 和序列权限。
- 单个节点的锁信息一定能反映完整的分布式死锁。
- 所有节点进程存在就代表集群健康。
- PostgreSQL 支持的功能在 OpenTenBase 中一定具有完全相同的行为。
